## 4. 关键技术发现（均为实测结论）

### 4.1 天空视窗的显示器
- 虚拟显示器 ID **90000005**，属主 `com.skyui.skylink.coreservice`，`uniqueId=virtual:com.skyui.skylink.coreservice,1000,com.nio.link.connly.five,0`
- flag 含 `FLAG_SECURE`（**所以车机屏无法截图**）、`FLAG_ROTATES_WITH_CONTENT`、`FLAG_PRESENTATION`

### 4.2 显示器尺寸/方向的真正机制
- 尺寸**不是**应用清单能定的，也**不能**事后改：
  - ❌ `wm size` 强改 → SkyLink 创建时写回，**且输入变换变成错误缩放（2.03×），触摸必然错位**
- 显示器**跟随前台应用请求的方向**（`FLAG_ROTATES_WITH_CONTENT`）：
  - 视频软件全屏播放能横屏，就是因为在**运行时请求了横屏**
  - 实测：我方 Activity 运行时 `requestedOrientation = SENSOR_LANDSCAPE` → `cur=3024x1696` ✅
- SkyLink 有专门的 **方向管理器** `SkyScreenCastOrientationManagerImpl`，会把应用判成三类：
  - 声明横屏的应用 → `user`（**跟随该显示器的用户旋转设置**）
  - Apple Music（清单为 `behind`）→ **强制竖屏 `1`**
- **结论**：只要把车机显示器的「用户旋转」设为横屏，被判定为 `user` 的应用就能 16:9 满屏

### 4.3 `mWindowType` 决定"镜像"还是"原生级"
- 日志 `BaseVirtualWindowManager: getVirtualDisplay mScreenType=1, mWindowType=X`
- `mWindowType=2` → 手机镜像（9:16）；`mWindowType=6` → **车机全屏/原生级（16:9）**
- **实测（2026-10-07 20:45 复核后降级为「存疑」）**：原文写"只有 `com.shihab.diplay/.CarPlayHostActivity` 能拿到 `mWindowType=6`"，
  但翻遍 `data/car-sessions/live/full.log`（5 万行，含 16:56–17:35 完整 CarPlay 会话）+ `data/logcat-天空视窗-2026-10-07.log`（51MB），
  **`mWindowType=6` 只出现在 `com.skyui.launcher/.SkyuiSecondaryDisplayLauncher`，diplay 一行都没打出过 6**。
  该说法大概率源自「CarPlay 会话建立时车机下发过一次 6」的一次性事件，不在日志窗口内。
  ⚠️ **拿到干净复现前不要当既定事实引用**。另：`CarPlayHostActivity` 实测**全程在 90000005**（从未上 90000001），
  但窗口是 **3024×1696 横屏已铺满车机屏** → 尺寸/横屏早已达标，缺的只是「车机端入口」。
  详见 `docs/log/未落文档的结论-补充.md` §1.1、§2
- 该判定**不受**下列因素影响（全部试过）：类名、taskAffinity、resizeableActivity、windowSoftInputMode、USB intent-filter、screenOrientation、configChanges、launchMode

### 4.5 Apple Music 的 DRM 报错 19623
- **现象**：天空视窗打开时启动播放 → "内容无授权"（19623）
- **实测结论**：
  - 与 root / 重打包 / Play 认证 / 区域 / GMS 版本**都无关**
  - ✅ **先关天空视窗 → 启动播放（拿到许可证）→ 再开天空视窗**，播放与切歌都正常
- **本质**：DRM 只在"开始播放"那一刻校验输出路径（虚拟显示器会被判为不安全输出）

### 4.6 Apple Music 可被外部读取/控制（media3）〔该能力仍成立，但对应界面已移除〕
- 它暴露：`com.apple.android.music/.player.MediaPlaybackService`
  - action：`androidx.media3.session.MediaSessionService` + `android.media.browse.MediaBrowserService`
- ✅ 用 media3 `MediaBrowser` 可连接（**旧版 MediaBrowser 会被拒**）
- ✅ 可读：正在播放（标题/歌手/专辑）、**封面 URL**、进度、**队列（含每首 mediaId）**
- ✅ 可控：播放/暂停/上一首/下一首/跳转、进度拖动（31 条命令）
- ❌ **资料库浏览被拒**（`getLibraryRoot` 返回 `code=-4`，只对 Android Auto 等系统客户端开放）
- 前置条件：清单里加 `<queries>`，否则 `getLaunchIntentForPackage` 返回 null

### 4.7 音频链路与"无损"
- 车机输出设备：**座舱音响** = `nio_virtual_devices`（IP 音频，PCM **无压缩**，端口支持 5.1 / 7.1.4）
- **安卓版 Apple Music 本地解码 → 直接 PCM 输出 → 无损**（不需要任何额外条件）
- ⚠️ CarPlay 路径**拿不到无损**：DiPlay 源码注释与实测均表明 **iPhone 只认 AAC-LC**（试过 PCM 与 ALAC）

### 4.8 其他环境事实
- 热点（DiPlay 自建）：SSID `carplay`、WPA2、密码 `<HOTSPOT_PASSWORD>`（**不要改**，iPhone 靠"已知网络"自动加入）
- 无线 CarPlay：iAP2 over BT → 加入 Wi-Fi AP；AirPlay TCP 7000；MFI 身份取自 `assets/offline-mfi/`
- 有线 CarPlay：Apple USB Multiplexor + NCM + usbmux
- 频段：系统热点实际跑 **2.4GHz ch11**（设置里显示"5GHz"是假象，因 NIO Link 的 P2P 组占用了 5GHz ch149）；"都要 5G"不可实现，2.4+5 双射频分流才是最优

### 4.9 AA 17.7 的 headunit-server（Self-Mode）断点 —— 已定位到组件级
- 环境：Android Auto **17.7.663654-release**（`com.google.android.projection.gearhead`）+ Open Headunit Revived **3.5.0-beta3**（`com.andrerinas.headunitrevived`，flavor=**github**，含 DummyVpnService）
- OHU 在 AA ≥ 17.4 时的 Self-Mode 只做一件事：**连 `127.0.0.1:5277`**（源码 `self/launchers/SelfLauncherV17_4.kt`，38 行；不发任何 intent、也不负责启动 headunit server）
- 实测握手过程：
  1. TCP 建连成功，AA 打日志 `GH.DHUService: Head unit connected`
  2. AA 的 `:car` 进程随即 `START u0 {act=com.google.android.gms.carsetup.START_DUPLEX cmp=…/com.google.android.apps.auto.carservice.gmscorecompat.FirstActivityImpl}`
  3. **`ActivityNotFoundException`（该 Activity 在清单里写死 `android:enabled="false"`）** → `GH.DHUService: Head unit disconnected`
  4. OHU 侧表现为 `Handshake: No VERSION_RESPONSE`（AA 一个字节都没回），界面停在 `正在等待你的手机`（= `R.string.stage_armed`，**是失败后的静止态文案**，不是等待中）
- **归因三连（都验过，排除"OHU 的锅"）**：
  - 用 **Google 官方 DHU 2.0**（`~/Library/Android/sdk/extras/google/auto/desktop-head-unit`）连同一个 server → **完全一样的 `START_DUPLEX` 失败**
  - 用 Mac 做 TCP 中继，让 AA 看到的对端是**另一台设备**（192.0.2.x）→ 仍然触发 `START_DUPLEX` ⇒ **与 loopback/自我判定无关**
  - `pm enable …/gmscorecompat.FirstActivityImpl` → `SecurityException: Shell cannot change component state`（无 root，`adb root` 被拒：`adbd cannot run as root in production builds`）
- 相关旁证：AA 在本机 **不是系统应用**（`flags` 里没有 `SYSTEM`/`UPDATED_SYSTEM_APP`，codePath 在 `/data/app`）→ 与 OHU issue #994（CN ROM "AA isn't installed as a system app"）吻合；OHU issue #977 里维护者称在他人设备上 5277 的 SSL 握手 100% 成功，说明**同一 AA 版本在不同设备上表现不同**
- 同版本里被 Google 关掉的其它入口（清单实测）：`…wireless.setup.service.impl.WirelessStartupActivity` = **exported=false**；`…wireless.setup.receiver.WirelessStartupReceiver` = **enabled=false**；`WifiBluetoothReceiver`（`START_WIRELESS_PROJECTION`）= 仍 enabled+exported

### 4.10 OHU 的可脚本化接口（不用碰屏幕就能驱动）

- AHU 日志 tag = **`OPENHU`**（`adb logcat -s OPENHU`），自带诊断文案（例如"对方接受连接后一个字节都没发"那段）

### 4.12 AA 17.3 实测：Self-Mode 走到"连上"了，但被 **CDM 特权权限** 拦死（**当前最本质的结论**）
降级到 **Android Auto 17.3.662804-release**（APKMirror 的 `(arm64-v8a)(120-640dpi)` apkm，装法见 §8）后复测，OHU 正确切到老路径：
```
SelfMode: AA < 17.4 detected. Starting WirelessServer on 5288 and running legacy triggers...
Wireless Server listening on port 5288
SelfMode: Launching AA Wireless Startup via Activity...   → 失败（17.3 里 WirelessStartupActivity 也是 exported=false）
SelfMode: Broadcast fallback 1 (WirelessStartupReceiver) sent.   → 这条路 AA 会响应 ✅
```
- AA 会真的连上 `127.0.0.1:5288`，AA 自己的埋点一路走到：
  `WIRELESS_WIFI_CAR_WIFI_SETUP_INITIALIZED → WIRELESS_WIFI_SOCKET_CONNECTED → CAR_CONNECTION_CDM_REQUESTED` → **连接被 reset**
- 崩溃原因（决定性证据）：
  ```
  SecurityException: Application must hold android.permission.REQUEST_COMPANION_PROFILE_AUTOMOTIVE_PROJECTION
  →（用 role 解决后）→ SecurityException: Application does not hold android.permission.REQUEST_COMPANION_SELF_MANAGED
  GH.CrashHandler: java.lang.IllegalStateException: Failed to register vehicle with CDM
  ```
- **两个权限的性质（`dumpsys package` 实测）**：
  | 权限 | protectionLevel | 能不能给 |
  |---|---|---|
  | `REQUEST_COMPANION_PROFILE_AUTOMOTIVE_PROJECTION` | `internal｜role` | ✅ **可以**：`cmd role add-role-holder android.app.role.SYSTEM_AUTOMOTIVE_PROJECTION com.google.android.projection.gearhead`（先 `cmd role set-bypassing-role-qualification true`）→ `granted=true, flags=[GRANTED_BY_ROLE]` |
  | `REQUEST_COMPANION_SELF_MANAGED` | `signature｜privileged` | ❌ `pm grant` 报 `not a changeable permission type`；换 `SYSTEM_COMPANION_DEVICE_PROVIDER` 角色也不行（GMS 占着且移除失败） |
- **本质**：这两个权限在正常手机上靠 **AA 是预装特权应用（/system/priv-app + privapp-permissions 白名单）** 获得；本机 **AA 是纯用户应用**（`pkgFlags` 无 `SYSTEM`）→ 无线投影的 CDM 注册必然失败。与 OHU issue **#994**（CN ROM "Android auto isn't installed as a system app"）完全吻合
- 附带事实：`cmd role` 的授予 **重启即失效**（重启后 role 空、权限回到 `granted=false`）；重启后 `svc power stayon usb` 也不再保持亮屏
- 结论：**在这台 NIO Phone 上，"AA 当手机侧、OHU 当车机侧"这条路被 OS 特权级别挡死**（无线必然要过 CDM）。有线 USB 投影理论上不过 CDM，但那需要跟真正的车机/USB 主机对接，单机自投影做不到
- **最终确认（同一天补测）**：AA 17.3 的 **headunit-server（5277）路径也倒在同一步** ——
  ```
  GH.DHUService: Head unit connected → GH.CarConnSessMgr: sendDeviceAppeared to CDM
  SecurityException: Application does not hold android.permission.REQUEST_COMPANION_SELF_MANAGED
  GH.CrashHandler: IllegalStateException: Failed to register vehicle with CDM
  ```
  即 **无线(5288) / 有线式(5277) 都要过 CDM**，与客户端是谁无关（OHU、Google DHU 2.0 都一样）
- **也确认了这台 ROM 没有 AA 的系统 stub**：`/system{,ext}/priv-app`、`/system{,ext}/app`、`/product/*`、`/my_product/*` 全部没有 gearhead；`pm install-existing` 也只是指回 `/data/app` 的那份。也就是说 **AA 在这台机器上永远是"纯用户应用"，永远拿不到 signature|privileged 权限** → 阶段二在"单机自投影"这一形态下**无解**（除非 root/改 system，或换一台 AA 是预装系统应用的设备当手机侧）

### 4.13 `mWindowType`（2=镜像 / 6=原生级）到底谁说了算 —— 反编译 SkyLink 的结论
把 `/system_ext/app/skylink/skylink.apk`（31 MB，可读）apktool 全量反编译后查到：
- 赋值只有两处 setter：`com/ucarmd/connectly/remoteapi/windowmanager/c;->E0(I)`（设 mWindowType）、`B0(I)`（设 mScreenType）
- mWindowType 的**真正的源头是车机**：`com/ucarmd/connectly/remoteapi/n.smali:2098` 处
  ```
  invoke-virtual {p1}, Lcom/databus/proto/CastScreenProto$ScreenInfo;->getWindowType()I
  move-result v0
  iput v0, p0, Lcom/ucarmd/connectly/remoteapi/n;->c:I        # 存起来
  ```
  而手机→车机的三个发送点（`n.smali:1223 / 1343 / 1612`）**全是把 `n.c` 原样回显**（`ScreenInfo.Builder.setWindowType(n.c)`；1612 那处是对 `type=1` 的消息硬编码 2）
- 也就是说 **16:9"原生级"不是手机能自己决定的，是 蔚来车机通过 databus protobuf（`CastScreenProto.ScreenInfo.windowType`）下发的**；手机照做。这就解释了 §4.3 的实测：白名单应用/自定义 Activity 都只能拿到 2，只有车机侧认定为 CarPlay 宿主（`com.shihab.diplay/.CarPlayHostActivity`）的才拿到 6
- 手机侧那条白名单（`assets/settings_config.json`）**没有可写杠杆**：
  - 缓存路径是 `Context.getFilesDir() + "/settings_config.json"`（即 `/data/data/com.skyui.skylink.coreservice/files/`）→ shell 写不了
  - 更新入口 `com.nio.base.config.ConfigUpdateReceiver` 虽然 `exported=true`，但带 `android:permission="com.skyui.netconfig.permissions.CONFIG_UPDATE"` → shell/第三方应用发不进去
  - `/sdcard/Android/data/com.skyui.skylink.coreservice/` 里只有 `car_transfer.txt`，没有配置
- **推论（对方案 D 第 2 步很关键）**：想拿 6，**唯一的手机侧杠杆是"让车机把我们认成它认识的那个包"**（包名/组件身份伪装）→ 也就是文档里的「NIO Link 白名单**精简壳**」；而且必须精简（上次完整拷贝伪装导致 NIO Link 闪退，见 §4.4）
- 另外发现几个**可写的系统开关**（`settings list global` 可见，shell 能改，值得后续试）：
  `skylink_feature_switch=15`、`skylink_inject_rotation=4`、`skylink_inject_rotation_value=0,10,0`、`skylink_cast_start`；代码里对应 `com/nio/util/virtual_display/b.smali`（**虚拟显示器旋转注入**）与 `com/nio/util/j.smali`（feature switch）

### 4.14 两个"绕开方向管理器"的开关 + 方向管理器内部结构（2026-10-07 反编译 + 实机验证）
**A. `wm set-ignore-orientation-request`（AOSP 标准，shell 可用，已实机验证）** —— 方案 D 第 1 步最有希望的一条：
```bash
adb shell wm get-ignore-orientation-request -d 0        # → ignoreOrientationRequest false for displayId=0
adb shell wm set-ignore-orientation-request -d 0 1      # 生效；读回 true
```
语义就是"**该显示器忽略应用请求的方向**"（AOSP 的 `DisplayContent.mIgnoreOrientationRequest`）。车机显示器上应当是 §4.2 那个"应用声明横屏却被方向管理器改写"问题的**标准解法**：先 `wm set-ignore-orientation-request -d 90000005 1`，再 `wm user-rotation -d 90000005 lock 1`，应用就应该跟随显示器横屏。

**B. `dumpsys window allPackagesFullscreen 0|1`（NIO 私有扩展命令）**
- 入口：NIO 把命令挂在 **`dumpsys window <cmd> <args>`** 上，实机日志确认收到：
  ```
  D ScreenCastController dumpCommand cmd=allPackagesFullscreen, args=[allPackagesFullscreen, 1], opti=1
  D SkyScreenResolutionManager: dumpCommand cmd=allPackagesFullscreen ...
  D RspLayoutControllerSkyImpl: dumpCommand cmd=allPackagesFullscreen ...
  ```
- 作用（反汇编 `skyui-services.jar` 得到）：`ScreenCastControllerSkyImpl.onCommand` → `dealAllowAllPackagesFullscreen` → `ScreenCastControllerSkyImpl` 设 `SkyScreenCastOrientationManagerImpl.mAllowAllPackagesFullScreen = 1`
- 这个字段的威力：`SkyScreenCastOrientationManagerImpl.isNeedLetterbox()` 里
  ```
  if (mAllowAllPackagesFullScreen == false) {  # 只有 false 才走白名单/系统应用等一系列检查
        isInFullScreenWhiteList(pkg) / applicationInfo.isSystemApp() / isSelfDevelopedRemovablePreinstalled() ...
  }
  ```
  ⇒ **= true 时跳过白名单，所有包都能"全屏"**（正是方案 D 想要的效果，且**不需要伪装壳**）
- ⚠️ **但很可能是 root 专用**：调用点前有 `enforceCallerIsRoot()`，实现是
  `if (Binder.getCallingUid() != 0) throw new SecurityException("Must be root to call SkyAMS shell commands")`。
  我们执行时**没有**在 logcat 里看到这个异常（可能被上层 try/catch 吞了），所以**到底生效没有，只能在车机上用效果验证**（脚本里作为第 D 组）

**C. 方向管理器的内部结构（`/system/framework/skyui-services.jar` → `classes.dex`）**
- 类：`com.android.server.wm.SkyScreenCastOrientationManagerImpl`（实现 `SkyScreenCastOrientationManagerStub`），配套 `SkyScreenCastLetterboxConfigManager`、`ScreenCastControllerSkyImpl`
- 关键字段：
  - `mAllowAllPackagesFullScreen: Z`（见 B）

- 读法（复现用）：`adb pull /system/framework/skyui-services.jar` → unzip 出 `classes.dex` → `dexdump -d classes.dex > dump.txt`（74 MB）→ 搜类名（我们就是这么读的）

### 4.15 另外两个 shell 可写的"旋转/布局"设置（框架与 SkyLink 都读它们）
**A. `skyui_custom_rotation`（Global，本机当前 = `-1`）**
- 写入方：SkyLink `com/nio/util/j.smali::O(I)`（日志 `setCameraRotation rotation:`，走 `DebugCmdExecutor`）
- 读取方：`/system/framework/skyui-framework.jar` → `android.app.ActivityThreadExtImpl`（**每个 app 进程各一份**）注册 SettingsObserver → `updateSkylinkCustomRotation()`，负值会被 clamp 成默认值
- **使用点（关键）**：只有当 `Display.isSkyLinkDisplay(currentDisplayId())` **且该显示器 `appWidth > appHeight`（即已经横屏）**时，框架把"应用感知到的 display rotation"**替换成 `mSkylinkCustomRotation`**；否则用真实 rotation。也就是说这是"让应用以为屏幕转到了某个角度"的兼容 hack
- 试法（车内 A/B，成本≈0）：`settings put global skyui_custom_rotation 0|1|2|3`，跑完恢复 `-1`

**B. `skylink_inject_rotation` / `skylink_inject_rotation_value`（Global）**
- SkyLink 侧：`com/nio/util/virtual_display/b.smali` = `VirtualDisplayOrientationUtil`
  - `startInject(int i)`：把 `skylink_inject_rotation` 写成 **4**，然后**每秒**在 `arr[i]` 与 `arr[i+4]` 之间交替写 `skylink_inject_rotation_value`
  - `arr` = `{"0,-10,0","10,0,0","0,10,0","-10,0,0","1,-10,0","10,1,0","1,10,0","-10,1,0"}`（本机当前值 `skylink_inject_rotation=4`、`skylink_inject_rotation_value=0,10,0`）
  - 另有 `start(int)` / 线程 `Orientation_Thread`
- 框架侧：`ActivityThreadExtImpl.updateSkylinkInjectRotation()` / `updateSkylinkInjectRotationValue()`（逗号分割 + `parseFloat`）
- 语义**未完全确认**（看起来是"每 1 秒微调一次，逼应用重算布局/方向"的 workaround），但两个 key 都是 shell 可写的 → 值得作为车内备选试探
- 复现：`adb pull /system/framework/skyui-framework.jar` → unzip → `dexdump -d classes.dex > /tmp/skyframe.dump`（266k 行）→ 搜 `mSkylinkCustomRotation` / `skylink_inject_rotation`

### 4.16 NIO Link 白名单的匹配规则（= 伪装壳的设计依据）
反编译 `skylink.apk` 的 `com/nio/base/config/bean/SettingsConfig`：
- 配置结构：`supportPkgList` 是 4 个 bizType 块 —— **`cross_dev_notify` / `cross_dev_app` / `cross_dev_game` / `free_window`**；每项字段：
  `pkgName / appName / appNameCharacters / minVer / screenType / type / immersive / support_min_window / appIcon`
  - APK 内置资产里只有 **12 个 app + 10 个 game**；文档 §4.4 那份 **45 个 app 的名单是车机下发后缓存的**（缓存路径见 §4.13）
  - 本机内置资产里出现过的取值：`screenType ∈ {1,3,4,5,7,9}`、`type ∈ {0,1,2}`、`immersive`（游戏=true）、`minVer`（如飞书 6060650）
- **匹配方式**：
  - `getCastSupportAppByName(String pkgName)` —— 按**包名**（`com/ucarmd/connectly/remoteapi/n.smali:165`、`b.smali:442` 在用）
  - `getCastSupportAppByNameAndUid(String pkgName, int uid)` —— 当 `uid == 0x3e7 (999)` 时进入"分身"分支
  - 条目带 `minVer` ⇒ **伪装壳的 `versionCode` 必须 ≥ minVer**（与 NioPlay 的 `-PnioCrossVer=<≥minVer>` 构建参数一致）
- **`checkAnyDoppelganger()` 不是反伪装**：它把检测到的"克隆/分身"应用**加进** support list（日志 `add the cloned doppelganger app into config support list!`）→ 说明"同名包"不会因为"像替身"被直接拒绝
- 其他相关 API：`getCastablePackageList / getCastableAppPackageList / getCastableGamePackageList / getInstalledCastApps / getSupportPkgByType / getPkgListDTOByType / isGame / isMeet / getWlcThreshold / handleDoppelgangerConfigChange`
- ⇒ **第 2 步的结论（已完成评估）**：想做"精简壳"，必须 ① 包名落在车机名单里 ② `versionCode ≥ minVer` ③ 只保留渲染目标 UI 的 launcher Activity，**不要**带 CarPlay/MFI/USB-accessory 全套（上次完整拷贝就是这么把 NIO Link 弄崩的，见 §4.4）；且最终能不能拿到 `windowType=6` **仍由车机决定**，手机侧无法自证

### 6.4 AA 版本关键事实

- 当前主流 AA 为 **17.4+**；**17.4 起 Google 封了第三方自动拉起**（`WirelessStartupActivity`/`WirelessStartupReceiver` 被禁用）→ 官方文档称 Self-Mode 只剩 "启动 headunit server" 一条路

- **版本选择（重要）**：
  - **AA ≥ 17.4**：OHU 走 `SelfLauncherV17_4`，只连 127.0.0.1:5277 → 在本机被 `START_DUPLEX`/`FirstActivityImpl` 断掉 ❌

  - 社区推荐 **17.2**（OHU issue #859），17.3.x 也在可用范围
  - **不要升到 17.8**（issue #985：17.8 上 Self-Mode 1~2 秒即断）

## 7.5 实测踩过的工具坑（重要）

| 坑 | 说明 |
|---|---|
| `am start -p <包名>` 启动 Apple Music | ❌ 常报 `unable to resolve Intent`（shell 可见性限制）→ 要由**应用内**发起，或显式组件 + `<queries>` |
| `screencap -d <车机显示器>` | ❌ 返回 0 字节（该显示器带 `FLAG_SECURE`）→ 车机画面**无法通过截图验证** |
| `uiautomator dump` | ❌ 只针对默认显示器，看不到车机显示器上的界面 |
| `pm disable-user` / `pm enable` 改第三方组件状态 | ❌ `SecurityException: Shell cannot change component state` → 只能由应用改**自己**的组件；无 root（`adb root` → `adbd cannot run as root in production builds`） |
| 手机处于 Doze | ❌ `screencap` 得到纯黑；需先唤醒 |
| Activity 的 `taskAffinity` 与 CarPlay 相同 | ❌ `am start` 会被路由到车机显示器上的 CarPlay 任务里 → 已改为独立 `.music` |
| 用 uiautomator 的 `text=` 节点坐标去 `input tap` | ❌ 文字节点（TextView）常常**不是**可点击节点，按钮本体在父节点上 → 必须用 `clickable="true"` 那个 `bounds`（例如"独立模式"按钮是 `[210,447][680,917]`，文字在 `[210,932][680,1025]`，按文字点必然无反应） |
| 手机进入安全锁屏（指纹/密码） | ❌ 所有 UI 自动化失效，`wm dismiss-keyguard` 也无效 → **必须我本人解锁**；建议 `svc power stayon usb` + `settings put system screen_off_timeout 1800000` |
| NIO ROM 的 `QuickFreezeManager` | ⚠️ 会冻结后台应用（实测 AA 与 OHU 都被冻过，投屏会话被打断）→ 手机保持唤醒/解锁、相关 App 保持前台更稳 |
| 只看 `/proc/net/tcp` 判断端口 | ❌ 本机监听常在 **`/proc/net/tcp6`** 里（32 位十六进制全 0 地址）→ 两个都要看 |
| 把 `/proc/net/tcp` 的 state `06` 当"已连接" | ❌ `06`=**TIME_WAIT**（已断开）；`01`=ESTABLISHED、`0A`=LISTEN |
| 用不出网的机器下 APK | ✅ 可用手机 Clash 代理：`adb forward tcp:7890 tcp:7890` + `curl -x http://127.0.0.1:7890 …`（apkmirror 通、Cloudflare 挑战页会挡；Uptodown/APKCombo 页面可取） |
| 想验证"是不是 Open Headunit 的锅" | ✅ 拿 Google 官方 **DHU 2.0**（`~/Library/Android/sdk/extras/google/auto/desktop-head-unit`，配 `adb forward tcp:5277 tcp:5277`）当对照，最干净 |
| 想验证"AA 是否按对端是不是本机来决定行为" | ✅ 在 Mac 上跑 TCP 中继（`/tmp/relay.py`：本地 5277 → 手机 192.0.2.10:5277），让 AA 看到的对端是另一台设备 |
| 不想碰屏幕就驱动 OHU | ✅ 用 `AutomationReceiver` 广播（见 4.10） |
