# 给 Agent 的技术路线验证指南

这份仓库可以作为**路线审查、实验设计与独立实现的起点**。它不是完整可构建工程：壳应用、完整本地桥接源码、配对持久化实现和原始设备日志没有公开。不要把阅读摘要、模拟画面或脚本语法通过写成“已复现”。

## 从哪里开始

按顺序读 [当前边界](PUBLICATION-NOTES.md) → [借壳与桥接机制](SHELL-BRIDGE.md) → [验证摘要](VERIFICATION.md) → [音频实测](AUDIO.md)，再查 [工具依赖](../tools/README.md) 与历史专题。

仓库记录的链路是：

```text
车机 App List
  → 白名单包名的壳取得 NIO Link 入口
  → 壳显示原生应用的编码画面，并回传触摸
  → 手机独立虚拟显示器中的 Apple Music / Spotify

音频：手机音乐应用 → NIO Link 座舱音频输出
```

## 分层验证，分别下结论

| 层级 | 所需条件 | 应得到的证据 |
|---|---|---|
| 静态审查 | 仓库及本地分析环境 | JSON/CSV 一致性、白名单匹配机制、工具所缺依赖；只能得出“记录与架构可检查” |
| 手机画布 | 自己的 NIO Phone、原版音乐应用、已授权调试环境；缺失模块需自行实现 | 目标应用实际所属显示器、当前几何、视频解码帧、触摸后应用状态变化 |
| 车机入口 | 官方 NIO Link 连接正常、兼容车辆、可用的最小入口壳 | 车机能出现并启动壳，壳实际落入跨端画布；入口成功不等于音乐桥接成功 |
| 整体体验 | 上述入口与桥接均成立，车辆停稳 | 实车画面、触摸、播放/切歌、退出重进与重连；另测黑边、黑屏和持续运行 |
| 音频 | 正在播放的曲目、同时采集的播放会话与音频状态 | 将应用与正在输出的音轨/路由关联；Apple Music Atmos 与 Spotify 分别验证 |

没有对应设备时可以完成静态审查和实验计划，不能验证车机入口、厂商设备认证或真实扬声器输出。

## 缺失实现怎么分解

以下是独立实现的模块需求，不是仓库已经提供的接口或完整协议规范：

- **最小入口壳**：与设备当前白名单匹配的包名及版本条件；只保留所需组件，先验证单纯进入壳的画布。
- **授权启动模块**：首次配对、手机本地 ADB / shell 连接、启动桥接；不能假设普通应用天然拥有 shell 权限。
- **画面接收模块**：匹配所用 scrcpy 版本的协议和会话元数据，解码后按比例显示。
- **输入模块**：按当前源画布和实际显示区域做坐标变换，正确处理黑边与方向变化。
- **会话模块**：EOF/断开重建、退出时释放编码与唤醒资源、会话令牌校验；不能误停其他应用或其他会话。

现有脚本引用的 `apps/am-landscape/bridge/classes.dex`、scrcpy 运行资产和采集目录未随仓库公开。不要声称仅运行 `arm-am-embedded.py` 就能从干净克隆复现全部流程。独立实现应放在自己的工程中，明确区分“作者原实现”与“自己的重实现”。

## 避免重走已失败的路线

- 不运行已作废的 `car-orientation-test.sh`，不以 `dumpsys window allPackagesFullscreen` 当作非 root 可用入口。
- 不用 `wm size` 事后修改车机尺寸；曾导致触摸映射错位。
- 不硬编码显示器 ID、UID、PID、sessionId 或画布尺寸；从本次连接实时读取。
- 不把包名占位描述为修改系统白名单；不把借壳描述为已取得厂商授权或跨品牌设备认证。
- 借用包名会与原应用冲突。若设备已有真正的 VidHub，不直接卸载或覆盖它来完成验证；先与设备所有者确认具体变更和恢复方式。
- 本机 Android Auto 单设备路线已经终止；研究其他设备时应明确那是新的环境与实验。

## 如何报告结果

记录设备型号、系统/车机/应用版本、最小操作步骤、期待与实际结果、证据类型及限制。分别标注：**本次观察**、**沿用作者记录**、**推断**、**待验证**。

作者已实车确认 Apple Music Atmos；独立复核时仍应检查自己的曲目与配置。`7.1.4` / `0x2d63f` 表示声道配置，不能单凭它推断源音轨无损、全部扬声器独立非零或长期稳定。播放页标识与解码批次耗时也不能替代完整音频、端到端延迟验证。

对外仅附脱敏后的证据摘要。去掉账号、序列号、VIN、网络名/地址、令牌、配对材料和密钥；不提交原始 bugreport、完整 logcat 或整个设备备份。

## 可直接交给 Agent 的提示词
